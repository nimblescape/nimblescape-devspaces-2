# Change log

Each section lists the changes of one released version. The release workflow
takes the section of a version as the notes of its GitHub release.

## 0.3.0

**Several GitHub accounts:** Devspaces uses every GitHub account of VS Code that you allowed for Devspaces, and the view shows one list for all of them. Each account loads its own list with its own token. A devspace belongs to the account that created it and always opens with that account; a new devspace uses the account with the highest permission on the repository. The tooltip of a row names the account, and with more than one account the row of a devspace starts with its login. **Start with Account…** in the context menu of a repository that two or more accounts can access starts the devspace of the account that you select. **Add GitHub Account…** in the title bar of the view adds an account, and Devspaces asks once about a GitHub account of VS Code that it does not use yet. A link asks GitHub with each account, and a course link opens the repository of the login in its name with that account. When an account leaves, only the windows of its devspaces close. **Remove Devspaces from This Docker Engine…** deletes the devspaces of all your accounts in Devspaces, if you agree. See [Several GitHub accounts](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#several-github-accounts).

**Always Open:** the question before a link creates a devspace of a repository of your account or of one of your organizations has a second button, **Always Open**. It opens the repository and turns off the new setting devspaces.confirmOpenFromLink, so later links, also course links, create such devspaces without the question. Turn the setting on again in the Settings editor to get the question back. A repository of another owner is always confirmed. See [Open from a link](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#open-from-a-link).

**Remote Docker host:** the window of a devspace on another computer reaches its Docker engine through a Docker pipe of Devspaces on your computer, and Devspaces carries those Docker connections, together with its helper container there, over one SSH login per window. Before, the Dev Containers extension started a new SSH login for each of its Docker calls, which an SSH server could refuse. The Docker calls of Devspaces itself on that computer use the same SSH login while it is open, without an SSH check before each operation, and so do its checks before that login starts the connection: the open of a window on another computer logs in to it once. A window that Open Recent kept from an earlier version still connects through its Docker context. See [Remote Docker host](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#remote-docker-host).

**Own list of remote hosts:** Devspaces keeps its own list of SSH hosts with Docker, and it no longer creates or switches Docker contexts. **Use a Remote Docker Host…** tests a host and then uses it without a question, and the `docker` command in your terminals keeps its Docker context. The list also shows the SSH hosts of your Docker contexts, and **Remove a Host from the List…** forgets a host. The window of a devspace always opens on the host of its devspace, without the question "Use `<host>` again?". **Ask Again Before Changing the Docker Host** and the "Don't Ask Again" buttons are gone. When the current Docker context of your computer reaches a host over SSH, the sidebar shows "Docker is set to `<host>` over SSH", Devspaces does nothing with Docker, and it offers that host once for its list.

**Docker CLI for remote hosts:** the window of a devspace on another computer runs the Dev Containers extension with a Docker CLI that Devspaces downloads from `download.docker.com` and checks against the size and SHA-256 in its code, and once it is there, Devspaces runs its own Docker calls on another computer with it too, in every window. Every computer connects with the same tested version, also when the Docker CLI of your computer is older or newer, and the Docker tools in your terminals keep their Docker CLI. The first such window downloads it once while it starts, and a notification shows the progress. When the download fails, the window uses the Docker CLI of your computer. See [Remote Docker host](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#what-to-know).

**Remote host without Docker on your computer:** without Docker, the Docker setup in the view offers **Use a Remote Docker Host…** next to the installation of Docker. On a computer without a Docker CLI, the command downloads the Docker CLI of Devspaces after you choose the host, and Devspaces then works with Docker on that host, without any Docker on your computer. **Use the Local Docker** shows the Docker setup again. See [Remote Docker host](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#set-up).

**SSH login without setup:** a remote host needs no SSH key and no host key that you accepted in a terminal before. When the SSH login to the host asks a question in a flow that you started (the test of **Use a Remote Docker Host…**, or a command such as **Start** with its progress notification), Devspaces asks it in VS Code: a dialog with the fingerprint of an unknown host key, which **Accept and Connect** keeps in your `known_hosts`, and an input box for your password, the passphrase of a key, or a code. Work in the background asks nothing. The test of a host now runs on one SSH login. See [SSH questions](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#ssh-questions).

**SSH key for the next logins:** after a login with your password to a remote host, Devspaces asks once whether to log in with a key next time. **Use a Key** creates the SSH key of Devspaces, `~/.ssh/devspaces_ed25519`, on your computer when it is not there yet, adds its public key to `~/.ssh/authorized_keys` of your account on the host on the same login, and tests it. Then every login of Devspaces to that host, also the work in the background and the Docker CLI, uses this key without a password. **Not for This Host** keeps the password for that host and is not asked again. See [A key for the next logins](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#a-key-for-the-next-logins).

**The WSL distribution of Devspaces (Windows):** a WSL distribution with the name `devspaces` and Docker Engine inside can be the Docker host of Devspaces, without Docker Desktop and without SSH. **Set Up Docker for Devspaces** in the Docker setup of the view (or **Set Up Docker for Devspaces in WSL…**) creates it for your Windows user without administrator permission: after one question with the downloads and the folder, it downloads the Debian file of the list of WSL distributions of Microsoft and checks its SHA-256, registers it with `wsl --install --from-file`, installs Docker Engine there from `download.docker.com` with systemd on, and then uses it. By default, the drives of Windows are not mounted there, and the start of Windows programs from there is off; these settings are no wall against root in the distribution (see [Security](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/security.md#remote-and-shared-engines)). **Remove the WSL Distribution of Devspaces…** deletes it after a warning. **Use a Remote Docker Host…** lists it as `wsl:devspaces` when it exists, also a distribution of that name that you made yourself, which Devspaces never changes. Devspaces reaches it with `wsl.exe` as root of the distribution, with the same relay, Docker pipes and Docker CLI of Devspaces as an SSH host. While a container runs there, Devspaces keeps the distribution running, also after VS Code closed, as Docker Desktop does, with `wslg.exe` of WSL, which opens no window. Its work in the background starts the distribution only when you answered **Keep Running** for its Monitor, and in the window of a devspace there; otherwise the view shows the devspaces there as stopped, with **Start**. With **Keep Running**, a start entry of your Windows user, `nimblescape Devspaces WSL devspaces`, starts the distribution and its Monitor when you log on to Windows; Devspaces removes it after **Stop When Idle** and with the distribution. The distribution is never the default distribution of WSL, so `wsl` without `-d` does not open it, and Devspaces warns when the WSL integration of Docker Desktop is on for it. See [The WSL distribution of Devspaces](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#the-wsl-distribution-of-devspaces-windows).

**Docker setup on Windows:** Devspaces finds Docker Desktop that is installed for your user only, in `%LOCALAPPDATA%\Programs\DockerDesktop`. The installer of Docker Desktop selects this installation by default. Before, the view still showed **Install Docker** after the installation, and a link that you opened in the browser asked again to install Docker, until VS Code and the browser started again. **Start Docker** also starts Docker Desktop from this folder, and the Dev Containers extension, which connects the window to the devspace, uses the same Docker CLI.

## 0.2.0

**Course links:** a course link `vscode://nimblescape.nimblescape-devspaces-2/course?repository=owner/name-<username>` opens your own repository of a course, for example the repository that GitHub Classroom creates for you when you accept an assignment. Devspaces asks for the GitHub sign-in first if you are not signed in, puts the login of the signed-in account in place of `<username>`, and then opens the repository as a link `/open?repository=owner/name` does. A course link without `<username>` gets `-<username>` at the end of the name. When Devspaces is not installed, VS Code first offers to install it from the Visual Studio Marketplace. The section [Course links](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/guide.md#course-links) of the user guide shows the link for a web page.

## 0.1.0

The first version.

**Devspaces:** the view lists the GitHub repositories that you can access and that contain a Dev Container configuration, grouped by owner. **Start** opens a repository in its own dev container, a devspace, and connects the VS Code window to it. Devspaces clones the repository into a Docker volume, builds the image and creates the container on the Docker of your computer, or on Docker on another computer that you reach over SSH. Git on your computer is not needed. The setting devspaces.defaultImage names an image that every repository can start from. A repository with several sources (several configurations, or a configuration and the default image) has one child row per source, and each child row is its own devspace.

**Background container:** on each Docker engine, the container devspaces-monitor keeps the images of your devspaces, the VS Code Server and your extensions up to date, prepares the next image of a devspace in advance, and stops a devspace a few minutes after its last window closes, unless you keep it running. The first Start or Rebuild on an engine, or Update All Images Now there, asks whether it keeps running there, also while VS Code is closed. Stop When Idle turns on the setting devspaces.stopMonitorWhenIdle, so the Monitor ends 5 minutes after the last devspace stopped, on each engine from the next start of a devspace or Update All Images Now there; until then, a Monitor that keeps running goes on. A Monitor that keeps running ends itself after 30 days in which no devspace was used on its engine.

**Remove Devspaces from This Docker Engine…:** the command removes the Monitor, the helper containers and images, and the shared volumes of Devspaces from the current Docker engine, after a confirmation. A second confirmation shows the recorded Git changes of your devspaces on the engine and asks whether they are deleted too.

**Safe updates:** when a newer image is available, Devspaces tells you before it updates the container (setting devspaces.updateContainer). The files in the workspace are kept.

**Open from a link:** a link `vscode://nimblescape.nimblescape-devspaces-2/open?repository=owner/name`, for example on a website, opens the repository in its devspace. Devspaces asks before a link creates a devspace.

**Switch and reopen:** **Switch Devspace…** and the status bar switch between your devspaces. When the window that you closed last was connected to a devspace, the next start of VS Code opens that devspace again.

**Remote Docker:** **Use a Remote Docker Host…** runs your devspaces on Docker on another computer that you reach over SSH. After you confirm, Devspaces creates a Docker context for it.

**Docker setup:** without Docker, the view shows the steps to install it: WSL 2 and Docker Desktop on Windows, Docker Desktop on macOS, and Docker Engine on Linux, each only after you confirm the commands. When the current Docker context cannot be read, the sidebar shows "Docker context cannot be read". When the `docker` command uses Podman, the sidebar shows "Podman is not supported".

**Security:** host access checks refuse configurations that reach into your computer, for example bind mounts, privileged mode or the Docker socket. Devspaces uses the GitHub sign-in of VS Code, stores no token, and collects no telemetry. It checks and pulls images first without a registry login. Before your first devspace, it does no Docker work. In Restricted Mode, only your user settings count. The top of the README and [Security](https://github.com/nimblescape/nimblescape-devspaces-2/blob/main/docs/security.md#what-devspaces-does-on-your-computer) say what Devspaces does on your computer.
